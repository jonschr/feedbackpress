# FeedbackPress 0.2.2

A self-hosted WordPress client review plugin. Requires WordPress 6.6+, PHP 8.1+, and a writable private attachment directory. Single-site activation; multisite/network activation is not supported in this initial release.

## Install and review

Upload the ZIP in Plugins → Add New → Upload Plugin, activate, then open Settings → FeedbackPress. Activation starts in **Everyone** mode. Guests enter their name and email once when they first interact; SameSite=Lax cookies remember that identity for one year. Logged-in reviewers use their WordPress display name automatically. Guest names are display identities, not verified accounts.

Leave feedback, or the C key, starts element selection. Press C again outside an input to exit placement or cancel the current draft; Escape also exits. V toggles the issues side panel using the same behavior as View issues. Both launchers show their shortcuts in instant tooltips. These single-key shortcuts leave native inputs, textareas, selects, rich-text editors, and custom input widgets alone; they also ignore modifiers, key repeat, and composition. Dropping a pin opens a compact composer connected to that pin, with an outlined comment field, attachment icon, close icon, and submit button; submitting closes it and returns to pin placement so you can immediately leave another note. The X cancels the current pin and returns to placement; Escape dismisses the active feedback interface and exits placement mode, as does reloading. A submitted save may finish in the background, but does not reopen the interface after Escape. Command+Enter (or Ctrl+Enter) submits the issue or reply; plain Enter inserts a new line. The attachment picker accepts multiple files, keeps earlier selections when adding more, and allows removing files before submission. The submit button tooltip shows the keyboard shortcut. Pins stay visible on the page even when the issues panel is closed, during placement, and while composing feedback. They follow the selected status and search filters, defaulting to To do + Review. A new numbered pin appears as soon as its issue is saved, while attachments finish uploading, and remains when placement resumes. View issues opens a compact all-pages list. Search issue text and all replies within the selected statuses using the compact search field. Search is case-insensitive; multiple words must all appear somewhere in the issue or its replies. Clear the field to restore the list. Sort by numeric issue number (the default), page, completion date (newest first), or last edited (newest first). Last edited includes creation, replies, status changes, and uploads. Completion date is the latest Done status for a currently completed issue; reopened issues have no completion date and sort after completed issues. Sorting never changes the selected statuses, so include Done to see completed work. Both list rows and the pin popup always show all four status icons beside the issue number, with the current icon highlighted instead of a written status label. Clicking the current status leaves it unchanged unless resolving a status conflict. Clipboard means To do, play means Doing, eye means Review, and check means Done. For the selected issue, 1 sets To do, 2 Doing, 3 Review, and 4 Done. Styled tooltips appear immediately on hover or keyboard focus, with shortcuts in small key badges. They stay inside the viewport and also work in attachment lightboxes. They are ignored while typing in inputs, replies, or editable page content, during composition, with modifier keys, and while saving. The highlighted row and popup previous/next controls make it possible to work through the list, including across pages and list pagination. The popup holds the conversation and replies. Each comment shows a clearly labeled author and separate date. Its automatic screenshot sits on the right beside the text; smaller uploaded-file thumbnails sit beneath the text on the left. The wider popup provides more conversation space while staying within the viewport. Attachment lightboxes also identify the comment author. Reply files are queued until the reply is sent, then linked to that comment; failed transfers can be retried without posting the reply twice. Existing files without comment metadata stay with the original issue comment. Images display thumbnails and PDFs display document tiles. Clicking opens a modal lightbox with image or native PDF preview, Download, and an X; Escape returns to the same issue. PDF viewing also offers Open PDF as a browser fallback. File bytes are fetched through the authenticated API and preview object URLs are released when leaving the issue. On mobile, View issues switches back to the list while retaining the selected row. Press P during pin placement for page-level feedback. Escape dismisses the active review interface in one step; inside an attachment lightbox it first closes that preview. Keyboard handling runs at window capture so page widgets cannot swallow Escape, status shortcuts, or form submission during bubbling. Page feedback is also available without selecting an element. Each issue includes a thread, viewport/browser context, screenshot, and optional attachments. Opening an issue from a pin, list, or direct link scrolls to its saved position inside the selected element. Selecting an issue for another page navigates there first. Nested scroll containers are revealed too; fixed elements remain in place, missing elements leave the issue accessible, and reduced-motion preferences are respected. Replies, uploads, and status refreshes do not reposition the document. The sidebar supports page/number ordering and paginated status filters. Sorting happens before pagination. Search, sort, status filter, and list position are retained within the browser tab when navigating between site pages. Background updates retrieve other reviewers’ changes while review tools are in use. Reload or change the sort/filter to reapply the list order.

- **To do:** default for new feedback.
- **Doing:** work in progress.
- **Review:** client approval or clarification needed.
- **Done:** resolved; agents may use this for fixes they have verified.

All environments use simple numeric references: #1, #2, #3. New feedback takes the next number after every number already known to that network, including deleted issues. Filtering, pagination, and status changes never renumber issues. Existing environment-prefixed references are converted to the next available numeric labels while existing plain numbers stay unchanged. If disconnected environments independently create the same next number, synchronization deterministically gives one of those new issues a later number. Corrections converge independently of delivery order or site clocks; internal UUIDs keep threads, attachments, and links attached to the same issue. Number corrections do not change last-edited or completion dates. Update participating installations together so every site displays the same corrected labels.

The status filter is a checkbox dropdown: choose any combination of To do, Doing, Review, and Done. Its default remains To do + Review. Selections persist within the browser tab, including an empty selection. Escape first closes the open filter menu; a subsequent Escape dismisses the interface. Each issue has a status-colored leading edge and a light hover tint matching that status, with a stronger selected tint. Status action hover colors match their destination. Done issues remain muted gray even when selected, with grayscale thumbnails; opening an attachment still shows its original colors. Anyone allowed to review can change status. Conflict notices list competing changes; choosing a status resolves the conflict. An agent should explain the change and its verification environment in a reply before updating status.

## Access and files

Settings offer Everyone, Logged-in administrators, or Disabled. These settings are local to each installation and do not sync. Administrators means WordPress users with `manage_options`. Each installation has its own agent API key, available in these settings. Network synchronization uses separate member credentials. Keep both private.

Images (PNG/JPEG/WebP/GIF) and PDFs are limited to 5 MB each. SVG, video, and arbitrary documents are rejected. Files never enter the Media Library and are served as downloads through permission-checked REST endpoints. Default storage is a plugin-owned directory beside the WordPress web root. If the parent is not writable, set `FEEDBACKPRESS_STORAGE_DIR` in wp-config.php to a writable path **outside** the public web root. A custom directory must not be shared between separate installations.

New files expire 90 days after upload by default; change this setting for future uploads. Expiration timestamps travel with attachments, so offline copies cannot extend their retention. Expired files are immediately unavailable through the API and physically removed on cleanup/sync. The issue and attachment metadata remain. Deactivating or uninstalling preserves data intentionally.

Screenshot rendering uses bundled html2canvas-pro 2.6.3 (MIT). It reconstructs the visible viewport; cross-origin images, embeds, video, complex effects, and sticky elements may differ. Form fields and `[data-feedbackpress-private]` elements are hidden in the capture clone. Other visible private content is not automatically detected. Screenshots are captured automatically for each new issue. Element-feedback screenshots include an amber pin marker with a white outline at the original clicked point; its location is baked into the image so later layout changes cannot move it. Page-level feedback has no location marker. Existing screenshots are unchanged. A failed screenshot never discards the comment.

General widget controls use a self-contained black, white, and gray palette; status indicators retain their semantic colors. Pin-placement instructions and the launch buttons share one bottom toolbar, centered on the same row on desktop and stacked on narrow screens.

## Connect a network

1. Open **Settings → FeedbackPress**. Click **Copy connection code** on a connected installation.
2. On the other installation, paste the code under **Have a code already?** and click **Connect this site**. The site type is suggested automatically; you can adjust Local/Remote after pasting. Registration adds the URL to the connection.
3. If starting with only a local copy, use **Add site** to enter the first remote URL, choose Remote, and save. Then copy the connection code to that exact remote URL. This preserves the existing connection and local feedback.
4. For hosts using HTTP Basic Auth, expand **Hosting password protection** under the remote URL and save its credentials before copying the code. The REST API does not bypass hosting authentication.

The unified site list has one Local/Remote choice for each URL. No network name is required. Codes expire after 24 hours and should be treated as passwords. Regular invitations authorize one registration; first-remote setup codes are URL-bound and rotate the temporary credential on installation.
The copy button confirms a successful clipboard write. If browser permissions block copying, it selects the generated code for Command+C or Ctrl+C. Server errors appear in the same area; no code is copied when generation fails.
Joining adopts the supplied network configuration. All participants must use this network protocol; compatibility with the earlier environment/key sync was intentionally omitted. This release preserves existing feedback on the current installation.

Removing a row creates a revocation that propagates to other active peers. Until those peers receive it, they may still accept that member. **Disconnect this site → Reset URL and disconnect** binds this installation to its current WordPress URL and starts a separate connection with new credentials and a blank feedback workspace; previous feedback remains in a separate database namespace. To return to another network, join it again with a fresh code.

Migrating the database keeps the same network and feedback. On its first WordPress request, a copy detects its actual home URL, reuses that URL's directory entry (or adds it), and creates its own credential. Copied membership authorizes registration during the next active exchange; no reconnect code is needed for routine migrations, including copying local over an existing remote. The original source keeps its identity. Existing issue numbers stay unchanged, and a database-only migration can retrieve missing screenshots and uploads through the normal file exchange. Update all participating copies to this version before relying on automatic registration.

If the only other copy is an unreachable local site, add the remote URL to local's site list once so local knows where to connect after the migration. There is no discovery service that can find an unknown remote URL. Independently installed sites still use connection codes. Removed URLs and revoked source credentials cannot automatically enroll again; explicit joining remains available for intentional reconnection. To make a clone a separate project, use **Disconnect this site**.

Shared URLs, credentials, and configuration history are stored as encoded values, so normal literal URL find/replace does not rewrite them. Encoding is not encryption. No migration-plugin hooks or preservation promises are required. A full database rollback can still restore older configuration; an active peer retaining newer configuration can supply missing events at the next exchange. Sync cannot recover information lost from every copy.

### When syncing runs

An authorized visitor landing on a page with the review tools starts an asynchronous sync through that installation’s REST API. The settings page does the same for administrators. Further review activity keeps checks active, with a hard **one initiated run per 60 seconds per installation**, shared across users and browser tabs. There is no Sync button. The troubleshooting command `wp feedbackpress sync` honors that gate too. Browser checks pause after two minutes without review interaction, and immediately when the tab is hidden. Returning or interacting resumes them. There is no recurring feedback-sync cron job or unattended hourly traffic.

Each participating installation initiates two-way exchanges with joined remote members. Remote sites never try to contact local entries. For example, a production change can push to staging during production review activity; local pulls from either remote when its reviewer next arrives or continues working. A local change reaches remotes on its next eligible active check. With no active reviewer, convergence waits until the next visit or manual check. This is relatively live polling while in use, not an always-on notification service.

The first local save is immediate and never waits for peer requests. Background snapshots update pins and issue data, append newly arriving issues, and preserve the positions of existing list rows. Typed replies keep their text, caret, and focus; popup redraws wait until editing finishes. A filter/sort change or reload reapplies the list order and membership.

An append-only `{prefix}feedbackpress_events` table stores issue, reply, status, and attachment events, partitioned by network UUID. Exchanges compare UUID inventories rather than copied sequence cursors, so retrying is idempotent and a restored database can recover missing events. Status and configuration changes reference their predecessor events. UTC timestamps describe when they happened, while causal parents detect concurrent changes even with different site time zones or skewed clocks. Configuration conflicts suspend the affected member rather than silently choosing its credentials; save the intended directory or join from a healthy member to resolve them.

Attachment metadata travels with events; missing images and PDFs transfer separately through private REST endpoints, with size/type/SHA-256 validation. Each exchange checks actual file availability, so a database-only copy or missing file is repaired without clearing old “sent” flags. Transfers use bounded batches and time budgets; later active checks continue remaining work. Expired files cannot be revived and cleanup includes archived networks. No recurring cleanup job is created; expired files become inaccessible immediately and are physically removed during active sync cleanup.

Peer requests are sequential REST requests identified as `FeedbackPress/<version> (+https://github.com/jonschr/feedbackpress)`, following [SiteDistrict’s service and crawler request rules](https://sitedistrict.com/service-and-crawler-request-rules). TLS verification stays enabled, redirects are disabled, and failures receive per-peer backoff. HTTP 429 honors Retry-After. A 403 may indicate a firewall or revoked membership; it is not automatically treated as a rate limit. Hosting Basic Auth uses the Authorization header, while network authentication uses separate FeedbackPress headers. On these routes, requests carrying plugin credentials or a browser nonce do not mistake hosting credentials for WordPress Application Passwords; the ordinary agent Application Password flow remains supported. Review-overlay code never receives member tokens or host passwords; administrator-only setup codes carry the credentials needed to connect.

### Connection log

Settings → FeedbackPress → Connection diagnostics shows recent sync results. The local encoded log is capped at **100 entries and 64 KB**, with entries older than **three days** excluded. It records UTC time, peer URL, operation, HTTP status, request duration, retries, and transfer totals. HTTP 401/403/429/500 and non-JSON login pages are distinguishable. Credentials, setup codes, request payloads, and response bodies are excluded.

From the WordPress root:

```sh
wp feedbackpress sync-log
wp feedbackpress sync
```

The first command only reads local diagnostics; the second initiates a cooldown-limited exchange. `GET sync/log` is administrator-and-nonce protected. Keep logs outside public pages when sharing diagnostics.

## Agent REST API

Base: `/wp-json/feedbackpress/v1/` (plain permalinks also support `/?rest_route=/feedbackpress/v1/...`). Use `X-FeedbackPress-Key: <this installation’s agent key>`, or an administrator Application Password over HTTPS. Never put the key in query strings, frontend code, or source control.

| Method | Path | Purpose |
|---|---|---|
| GET | `issues?order=number&status=todo,review&page=1` | List up to 50 matching issues; optional search, path, order=page/number/completed/updated, and focus={issue UUID} |
| GET | `issues/{uuid}` | Full issue, status revision, thread, files, context |
| POST | `issues` | Create: `author`, `body`, `path`, `target` (`selector`, `text`, `x`, `y`), optional `viewport` |
| POST | `issues/{uuid}/replies` | Add `author`, `body`; response includes the new `reply_id` |
| POST | `issues/{uuid}/status` | Set `author`, `status`, `revision` |
| POST | `issues/{uuid}/files` | Multipart `file`; optional `screenshot=1` and `comment_id` (reply UUID or the issue UUID for the original comment) |
| GET | `files/{uuid}` | Download an unexpired attachment |

Lists default to natural issue-number ordering across all pages; `order=page` groups by page, then issue number. `order=number` sorts across pages by issue reference. `order=completed` and `order=updated` sort newest first by the returned `completed_at` and `updated_at` UTC timestamps, with natural issue references breaking ties and incomplete issues last for completion order. `search` matches all whitespace-separated terms, case-insensitively, across the original issue body and every reply. Search and status/path filters apply before sorting and pagination; `status=none` selects no statuses. `focus` chooses the list page containing a matching issue. Status values are `todo`, `doing`, `review`, `done`. Read the issue first and send its current `revision` with a status update. HTTP 409 means it changed: fetch again, inspect, and decide. Replies do not need a status revision. To associate files with a reply, use the returned `reply_id` as `comment_id` when uploading. The server rejects comment IDs not belonging to that issue; omitted comment IDs mean the original issue comment. The association is preserved by sync. Public GET endpoints follow review visibility; browser writes require a REST nonce and same-origin checks.

Sync-only endpoints `sync/exchange` and `sync/files/{uuid}` require the registered member’s `X-FeedbackPress-Network`, `X-FeedbackPress-Member`, and `X-FeedbackPress-Token` headers. Only the exchange endpoint can also register a migrated URL using a valid copied member credential in its private `copy` payload; a network ID alone cannot authorize it. File routes require established membership. These credentials are separate from the agent API key. Configured members are trusted peers. `POST sync/activity` is available to authorized reviewers with the normal browser nonce or to agents, and observes the same installation-wide cooldown. `POST network/code` is administrator-only; `POST network/join` authorizes registration using an unexpired, single-use invitation. No external SaaS service is required.

## Verification

Run `wp --path=/path/to/site eval-file /path/to/feedbackpress/tests/integration.php` on a local test site. It checks creation, replies, statuses, stale writes, conflicting offline changes, resolution, privacy, invalid uploads, expiration, and idempotency; test issues are removed in `finally`. Run `php tests/network-sync.php` for isolated three-site/configuration/file/HTTP-error checks using PDO SQLite and no external requests. `node tests/activity-sync.cjs` checks browser landing/live updates, idle/hidden pauses, reply preservation, and error recovery. Run `php tests/search-sort.php` for standalone search/date-sort checks without a database. With Playwright available and Chrome installed, `node tests/tooltips.cjs` checks instant tooltips using intercepted fixtures without changing client feedback. `node tests/screenshot-pin.cjs` checks marked screenshot uploads using the bundled renderer and intercepted writes. `node tests/passive-pins.cjs` checks passive visibility, filters, immediate saved pins, and delayed requests without touching client feedback. `node tests/navigation-shortcuts.cjs` checks C/V actions, tooltip badges, and typing guards. Run PHP lint and `node --check assets/review.js` after edits.

Initial release limits: no notifications, video, deletion UI, assignments, or automated code changes. The REST API supplies feedback to an agent; it does not run an agent. Public review mode intentionally permits visitors to see feedback and change statuses. Basic per-IP write throttling is included; public internet deployments may need edge-level abuse protection appropriate to their traffic.

## Plugin updates

FeedbackPress uses bundled Plugin Update Checker 5.6 to read `update.json` from this repository’s `main` branch. Its download URL points to a numbered GitHub tag archive, matching Recently Edited and Ollie Bridge. Plugin update checks are separate from feedback synchronization.

For each release, update the plugin header, `FeedbackPress\VERSION`, and `update.json` to the same version, and set `download_url` to that tag’s ZIP. Publish the matching tag (for example `0.2.0`, without a `v` prefix) and the manifest on `main`. Keep older tags unchanged. WordPress can then offer the newer version through its normal plugin updates UI.

Run `wp eval-file tests/update-checker.php` from this plugin directory to check registration and JSON parsing using intercepted metadata. Run `wp --require=tests/update-checker.php eval-file tests/update-checker.php` to verify update-AJAX boot. The tests simulate an update offer in memory and do not install it or save the synthetic version.

Changing a status updates its existing card in place. Its position, neighboring issues, and previous/next navigation stay stable while you continue reviewing, even if the new status falls outside the selected filter or changes its date-sort position. Reloading or explicitly changing search, filters, sort, or list page rebuilds the list. Passive page pins still follow the current filters.

## Authors

Guests identify themselves with a name and email before commenting. Logged-in reviewers use their WordPress account. An author identifier derives from the normalized email, independently of WordPress numeric IDs, and travels with issues and replies. Each installation displays its matching WordPress user’s display name; otherwise it uses the captured name. Guest identity is self-reported. Raw email addresses are not stored in feedback events or returned in feedback/author-list responses.

Click the issue author’s name in its popup to choose another person, or select Add person and enter a name/email. This changes the original issue author; reply authors remain attached to their own comments. Existing name-only authors are labeled in the picker until reassigned to an email identity. Author changes synchronize with causal revisions; conflicting changes can be resolved by choosing an author again. Update all participating installations to 0.2.2 before synchronizing author events.

API: GET `authors` lists available `{id,name}` identities without email addresses. POST `authors` with `name,email` adds a person. POST `issues/{uuid}/author` with `author_id,revision` (the issue’s `author_revision`) reassigns its author; stale revisions return 409. Guest/agent issue and reply creation accepts `author,author_email`; agents may instead supply a known `author_id`. Logged-in browser comments use the current WordPress account.

## Move a pin

Drag an existing numbered pin onto another element on the same page to correct its placement. Mouse and touch dragging are supported. A small movement threshold preserves normal click-to-open behavior. Escape or a cancelled touch gesture restores the saved position; a failed save also restores it and shows the error. Issue numbers, status, replies, and original screenshots stay unchanged. The new element selector and relative point are saved in a causal target event and synchronize with the issue. Concurrent moves are flagged; drag to the intended position again to resolve them.

API: POST `issues/{uuid}/target` with `author`, `target` (`selector`, `text`, normalized `x`,`y`), and the issue’s `target_revision`. Stale revisions return 409. All peers must have the new target-event support before synchronizing moves.

## Issue titles and descriptions

New notes have a required short title (up to 120 characters) and a separate description. The sidebar shows the title on at most two lines, with the author in smaller text beside the numeric issue number. The popup shows the full title and description. Search includes titles, descriptions, and replies. Existing notes receive a short display title derived from their description; their saved text is unchanged. API issue creation accepts `title` and `body` (description). Clients omitting `title` receive the same automatic fallback. Titles travel with issue events during synchronization.

The new-issue composer shows all four status icons, with To do selected initially. Choose a different icon before submitting to create the issue in that status; the choice is saved and synchronized. Each fresh issue starts with To do selected again.

Video-backed screenshot layouts: FeedbackPress preserves each video’s computed positioning on the renderer’s replacement canvas, so background videos do not push surrounding content out of place. This fixes new captures; it does not rewrite earlier screenshots. Cross-origin video pixels may remain unavailable under browser canvas security restrictions.

## Edit your comments

Comments matching the current reviewer’s email identity show an Edit action. The issue author can edit its title and description; reply authors can edit their own reply text. Save or Command/Ctrl+Enter applies the change; Cancel or Escape discards the edit draft. An Edited label records that content changed. Unsaved new replies and comment attachments remain intact.

The API checks the current author identity rather than trusting display names. Guest identities retain the existing self-reported name/email behavior; this feature does not add email verification. Older name-only identities cannot be matched to an email by guessing a name. Original issue authors can be reassigned through the existing author picker.

Edits append immutable events and synchronize using causal revision heads, retaining comment IDs and attachments. Concurrent edits are flagged for resolution. A stale save keeps the draft and offers an explicit discard/reload action, preventing silent replacement of another edit. Search uses the current title/description/reply text. Update remote copies before exchanging the new edit events.

API: POST `issues/{issue UUID}/comments/{comment UUID}` with `body`, `revision` (the comment’s `edit_revision`), and the normal author identity. Include `title` for an original issue edit. Ownership mismatches return 403; stale revisions return 409. Reply edit metadata is returned in its activity payload.

## Review layout

View issues opens a 400px drawer flush to the right, top, and bottom, with a fixed search/filter header and a scrolling list. It fills smaller screens. The bottom launchers hide while browsing; use the header plus button or C to leave feedback, and X or V to dismiss the drawer. Below 900px, opening an issue switches to its pin popup; its X returns to the list. Inter is bundled locally, with a system sans fallback. Automatic background updates replace the manual Refresh icon; a failed list read offers Try again. Existing filters, shortcuts, pin placement, status editing, and comment/media workflows are retained.

The issue rows extend to the edges of the scrolling area below the fixed tools. Drawer visibility and list position are remembered per browser tab alongside search, sort, statuses, and pagination. Following an issue onto another page or using a normal site link restores that context; reload and Back retain it too. Selecting an issue still locates its pin on the website without shifting an existing sidebar position. Changing search, sort, status filters, or list pagination deliberately returns the list to the top.
